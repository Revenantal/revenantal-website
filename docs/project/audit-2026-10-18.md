## Findings

### F01 — High: a compact registry breaks the staged channel lineup

Evidence: [data-model.md](../architecture/data-model.md), line 133; [channel-rules.md](../channels/channel-rules.md), line 25; [build-plan.md](build-plan.md), line 67; [channels/README.md](../channels/README.md), lineup table.

The registry lists built manifests in dial order, and positions after the last entry become NO SIGNAL. Launch contains only TV Guide and Status, but they must occupy positions 1 and 10. A compact array containing those two manifests puts Status at position 2. Later insertion of other channels also changes existing deep links and saved positions.

Recommendation: specify a stable 12-position registry with explicit empty slots, or give manifests stable dial positions and resolve by position. Test the launch lineup, SERVERS button, channel-10 hash and saved positions before adding the remaining channels.

### F02 — High: the live-data volume can hide the deployed site

Evidence: [hosting-and-ci.md](../architecture/hosting-and-ci.md), lines 16–17; [live-data.md](../architecture/live-data.md), line 15.

The live job writes to a shared volume mounted at the app's public folder, while Caddy serves the image's build output. If that public folder is the served output directory, mounting it hides the image's files; a populated named volume can also retain an old site across image updates. If it instead means Vite's source public directory, writes there will not update an already-built dist directory. The serving and mount paths are not defined sufficiently to avoid either outcome.

Recommendation: keep immutable site files in the image. Mount a dedicated runtime-data directory read-only into the web container and route only /live.json to it. Mount that directory read-write into the live job. Verify a second deployment changes index.html and hashed assets while preserving live.json.

Docker documents that mounted volumes obscure pre-existing container files: [Docker volumes](https://docs.docker.com/engine/storage/volumes/).

### F03 — High: stale values can continue to look live indefinitely

Evidence: [live-data.md](../architecture/live-data.md), lines 14–15 and 21; [data-model.md](../architecture/data-model.md), lines 91–104; [10-status.md](../channels/10-status.md), lines 42–51.

A failing source retains its previous value. Live has only one global fetchedAt, so a successful job can give old Steam, GitHub or project-status values a new timestamp. If the entire job stops, an old live.json can still load successfully and display green states indefinitely. The server-file 15-minute rule only runs when the job runs. Status additionally promises a next-poll countdown although the browser fetches once and never receives the next update.

Recommendation: retain per-source successful-fetch timestamps, define a maximum display age, and expose stale/unknown states without requiring polling. Age an already-open page using its clock. Label the Status footer as snapshot age or scheduled server refresh rather than implying the displayed page will update. Test partial-source failure, a stopped agent, a stopped job and an old cached snapshot.

### F04 — Medium: ChannelProps cannot supply several required features

Evidence: [channel-rules.md](../channels/channel-rules.md), lines 10–22; [03-terminal.md](../channels/03-terminal.md), line 25; [02-rev-os.md](../channels/02-rev-os.md), line 25; [08-late-show.md](../channels/08-late-show.md), data and acceptance sections; [data-model.md](../architecture/data-model.md), Site type.

Terminal must show shared credits, but credits are absent from ChannelProps. Broadcast playlists exist in content/broadcast.json but are absent from both Site and ChannelProps. Rev OS must power off through a link action, but no power action or URL protocol exists. Captions must persist through rv-settings, but no caption state or setter is passed to channels.

Following the contract literally makes these features impossible without hard-coded data or forbidden store/content imports.

Recommendation: define the smallest typed data props and host callbacks needed for credits, playlists, shutdown and captions. Add fixtures demonstrating each before those channels are built. Keep channels independent of the store.

### F05 — Medium: the audio contract only defines one-shot playback

Evidence: [channel-rules.md](../channels/channel-rules.md), play prop and direct-audio prohibition; [audio.md](../tv/audio.md), Channels and Audio; [soundscapes.md](../channels/soundscapes.md), Rules.

Channels may only call play(sound), which returns void. Requirements also include continuous music, an engine drone, projector/server hum, fades, OSD ducking and stopping when inactive. There is no manifest audio description, loop lifecycle API or ownership model for these sounds. An unbounded one-shot API cannot express these behaviors reliably.

Recommendation: define host-owned loop lifecycle and mixing behavior, preferably using manifest metadata for steady background loops and a small typed interface for dynamic sounds. Specify how tune-away, mute, tab visibility and unmount stop or suspend them. Keep Web Audio nodes inside the audio module.

### F06 — Medium: phase 1 depends on interfaces scheduled for later phases

Evidence: [build-plan.md](build-plan.md), tasks 1.6–1.10, 2.2 and 3.1; [controls.md](../tv/controls.md), Store Actions; [overview.md](../architecture/overview.md), Rules.

Phase 1 requires controls, effects, audio and persistence to use store actions, and a channel host to consume manifests. The store is scheduled at 2.2 and the channel contract at 3.1. The plan forbids starting a later phase until the earlier gate passes. A literal implementation either invents temporary interfaces or violates the stated sequence.

Recommendation: explicitly include the minimal UI-state store, manifest types and host contract in phase 1. Keep content loading and merging in 2.2 and the full channel contract suite in 3.1. This is a proposed clarification, not an approved build-order change.

### F07 — Medium: forecast privacy depends on unspecified proxy and cache behavior

Evidence: [forecast-and-radar.md](../architecture/forecast-and-radar.md), endpoint and privacy sections; [hosting-and-ci.md](../architecture/hosting-and-ci.md), forecast routing.

The same GET /api/forecast URL returns visitor-specific city information. The specification does not define trusted proxy handling, response cache headers, or access-log suppression in the reverse proxy. An application that sees only the proxy IP can locate the server instead of the visitor; an incorrectly shared HTTP cache can serve another visitor's city. Disabling application logs alone does not establish the promise that IPs are never logged.

Recommendation: define the trusted proxy chain and reject untrusted forwarded headers. Keep the city-keyed upstream forecast cache separate from visitor responses; specify private, no-store responses. Audit proxy and application access logs, bound cache size, and apply request limits and upstream timeouts. Test two visitors in different cities and DNT/Save-Data requests. These are design gaps, not observed leaks.

Direct radar/base-map requests also disclose a visitor's network address and requested map region to those providers. Record the chosen delivery behavior and explain it accurately in the privacy text. Open-Meteo documents upstream logging that can contain coordinates: [Open-Meteo terms and privacy](https://open-meteo.com/en/terms).

### F08 — Medium: the specified numeral geometry cannot meet the stated hit-area rule by simple enlargement

Evidence: [tv/README.md](../tv/README.md), line 40; [art-and-assets.md](../tv/art-and-assets.md), dial anchor table; [door-tv.dc.html](../reference/prototypes/door-tv.dc.html), lines 953–957.

At 1280×650, the stage scale is 0.634765625. A 44-pixel screen target needs about 69.32 stage pixels. The 12 numerals on a 64-stage-pixel-radius ring have adjacent centers only about 21.03 screen pixels apart. Enlarging each numeral to a conventional 44×44 hit box creates substantial overlap; the prototype's 24×18 stage boxes are only about 15.23×11.43 screen pixels.

Recommendation: resolve the project's 44-pixel requirement with a different interaction layout or a keyboard-accessible channel selector whose targets fit. Validate actual pointer regions and focus order at the minimum viewport. This is a conflict with the project's own target-size requirement, not a blanket claim that WCAG AA always requires 44 pixels.

### F09 — Medium: the checked-in board renderer cannot reproduce the mockups from this layout

Evidence: [render-boards.js](../reference/prototypes/render-boards.js), lines 4, 15 and 18; [reference/README.md](../reference/README.md), Using the Prototypes.

PROJ resolves to docs/reference/rev/project, which does not exist. Boards actually live under prototypes/boards; the mapped rack, Guide and Revscape assets live under separate reference/assets subdirectories. Installing Playwright does not repair those paths. The blob mapping also excludes the canonical TV's image and processed-sound references. Canvas support.js and runtime dependencies are not included, as the reference README partly acknowledges.

Recommendation: repair the local renderer's input and asset roots, document its dependencies and command, and state explicitly which prototypes still require the canvas. Add TV asset mappings if local TV reproduction is intended. Run a clean-checkout smoke render before using it as a visual acceptance tool.

### F10 — Medium: weather credits need placement in the forecast itself

Evidence: [forecast-and-radar.md](../architecture/forecast-and-radar.md), Radar and Credits; [01-tv-guide.md](../channels/01-tv-guide.md), Build Notes.

The plan places credits on a credits page, behind the settings door and in CREDITS.md. It does not require an Open-Meteo attribution link next to the displayed forecast. Open-Meteo's own guidance requests that placement. The base-map provider is also unspecified, so its attribution and permitted tile usage cannot yet be verified.

Recommendation: reserve readable attribution space in the forecast/radar panel, identify the base-map provider before task 3.5, and retain the central credits entries. RainViewer is currently suitable for personal/small community use, but requests visible credit and best-effort fallback behavior. Its documented maximum tile zoom is 7; account for that in the map design.

Sources: [Open-Meteo attribution guidance](https://github.com/open-meteo/open-meteo), [RainViewer API terms](https://www.rainviewer.com/api.html), [RainViewer tile documentation](https://www.rainviewer.com/api/weather-maps-api.html). This is a documentation/implementation requirement finding, not a legal clearance of any asset.

### F11 — Medium: the film lineup conflicts with the content brief

Evidence: [project-brief.md](project-brief.md), Design Direction; [channel-rules.md](../channels/channel-rules.md), line 78; [08-late-show.md](../channels/08-late-show.md), lines 23–25; [asset-checklist.md](asset-checklist.md), Broadcast media.

The brief prohibits gothic and death themes, while The Late Show explicitly selects Nosferatu and later Dracula. The decision log does not record an exception. Public-domain eligibility would not resolve this content-direction conflict.

Recommendation: choose films consistent with the brief, or obtain and record an explicit owner-approved exception before media production. Separately verify each exact picture and soundtrack edition in the required territories; calendar dates and film titles alone do not clear a particular upload.

### F12 — Low: root settings.json is a misplaced Markdown template

Evidence: `settings.json` (removed in follow-up), line 1; [.github/pull_request_template.md](../../.github/pull_request_template.md).

The root file contains the pull-request template rather than JSON. JSON.parse fails at the opening # Context. It is not currently consumed by application code, so there is no demonstrated runtime failure, but it is misleading configuration and will fail a JSON formatter/parser if included in tooling.

Recommendation: remove the accidental duplicate or rename it to a Markdown file if it has a separate purpose. Preserve the actual PR template and .claude/settings.json.

## Additional observations

- The project has clear ownership boundaries, a documented decision hierarchy, privacy constraints, graceful missing-data goals and explicit performance budgets. The current problem is completing the interfaces and operational details needed to enforce them.
- The canonical prototype intentionally differs from approved specifications: it still has The House and old channel positions, canvas-hosted blob dependencies, Google Fonts and a different live-data shape. Reference docs already say to rewrite it. Do not treat those known reference differences as production regressions or silently copy them into phase 1.
- A focused logic check confirmed that setting the prototype's reduced flag still produces a 3.3-second warm-up string on manual power-on. Production must implement the reduced-motion rule explicitly; the prototype is not evidence that accessibility acceptance has passed.
- The present frame.webp is 107,308 bytes. That alone fits the planned 160 KB first-paint image budget; the full asset set and actual requests still need measurement. Large source WAV/PNG files under reference/ are not proof of a runtime budget breach.
- Before committing real API fixtures, redact tokens, usernames belonging to other players, private allocations and unnecessary personal fields. The instruction to save real responses needs this handling step.
- Keep raw diagnostic errors out of public live.json. Its errors field is described as debugging-only but is part of a public document; use bounded public error codes and private logs.
- Before launch, verify browser cache policy, MIME types, security headers, URL-scheme validation, timeouts and redirect policy for project checks, sanitized public server fields, read-only mounts, SSH host-key verification, atomic agent uploads, and concurrency-safe deployments. These are unverified implementation checks, not vulnerabilities demonstrated in absent code.
- Documentation describes hook and CI enforcement in present tense, but neither exists yet. The planning status is clear; avoid relying on that enforcement until tasks 1.2–1.3 are complete.

## Recommended order

1. Establish a reviewed, committed baseline without removing existing work. Resolve F01–F03 and F06 before building the channel host, deployment and data pipeline.
2. Finalize the channel/audio contracts, target geometry and forecast behavior (F04–F08).
3. Repair reference reproducibility and the accidental configuration file (F09, F12).
4. Resolve attribution/provider choices and content direction before weather/media work (F10–F11).
5. Run the planned format, lint, type-check, tests and build after scaffolding. At the appropriate gates, verify keyboard/screen-reader behavior, reduced motion, mobile/List mode, malformed/stale data, no-WebGL fallback, broadcast synchronization, cold-load budgets and a deployment followed by rollback.

This audit proposes changes only. It does not approve new architecture decisions, alter the brief, implement fixes or certify the future deployment.
